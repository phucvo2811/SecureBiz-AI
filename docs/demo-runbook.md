# Thesis demo runbook

## Purpose

This runbook demonstrates the implemented chain using system-generated records rather than frontend hard-coded data:

`authenticated employee → business operation → structured activity → feature snapshot → persisted ML model → explainable risk assessment → security alert → investigation/citation-based copilot`

## Before the demonstration

1. Copy `.env.example` to the untracked `.env` file and replace every placeholder secret.
2. Start the stack with `docker compose up --build` on a Docker-capable machine.
3. Confirm the web application, backend health, AI health, PostgreSQL, Redis and S3-compatible object storage are healthy.
4. Bootstrap the first OWNER only on the empty database, then remove the bootstrap password from the environment and restart the backend.
5. Run `scripts/verify.ps1` before loading demo data. Pass `-PythonExecutable <path>` when Python is not on `PATH`.
6. Train or mount a recorded model artifact whose feature schema matches `behavior-v1`; record the artifact digest and model version.

Do not use the synthetic-v1 scores as a claim of production detection accuracy. They are reproducibility evidence only.

## Ready-made local accounts

When `DEMO_DATA_ENABLED=true`, the backend creates the following accounts. Their
shared password comes from `DEMO_ACCOUNT_PASSWORD` (the local default is
`SecureBiz@123`). These accounts and the accompanying dataset are for local
demonstration only.

| Username | Role | Suggested screen to verify |
|---|---|---|
| `demo.owner` | OWNER | All modules and reports |
| `demo.admin` | IT_ADMIN | Accounts, diagnostics and Security Center |
| `demo.manager` | MANAGER | Purchasing, customers and reports |
| `demo.sales` | SALES | POS, orders, customers and returns |
| `demo.warehouse` | WAREHOUSE | Inventory, transfers and stocktakes |
| `demo.accountant` | ACCOUNTANT | Orders, returns and reports |
| `demo.hr` | HR | Employees and departments |

The repeatable seed includes departments and employees, eight products with ten
SKUs, two warehouses, inventory balances, four suppliers, purchase orders and a
goods receipt, six customers, fourteen completed sales, invoices and payments,
a completed refund, a pending transfer and stocktake, audit history, and one
high-risk security alert. Restarting the backend does not duplicate these rows.

## Business-control scenario

1. As OWNER, create two employees with separate accounts and the least permissions needed for seller and approver duties.
2. Create a category, product variant/SKU, warehouse and supplier.
3. Create and submit a purchase order. Approve it with the second account and receive it once.
4. Confirm the inventory balance and immutable `PURCHASE_RECEIPT` ledger entry.
5. Checkout the SKU in POS and confirm payment, invoice, stock decrement and `SALE` ledger entry.
6. Create a partial or full return with the seller account; approve it with a different authorized account.
7. Confirm the bounded refund, original order history, optional restock and `RETURN` ledger entry.

The automated PostgreSQL integration test covers sale/return consistency and a two-transaction last-SKU race where exactly one checkout succeeds.

## Security-intelligence scenario

1. Perform normal activity with the demo employee across several windows so exported observations can form a chronological baseline.
2. In the isolated demo environment, generate a visibly different window using authorized test actions: repeated denied access plus unusually large/frequent inventory adjustments. Never perform these test actions in production data.
3. As an authorized security administrator, request analysis for that employee and time window.
4. Open Security Center and verify the stored model version, anomaly score, risk-policy version, normalized risk score, contribution reasons, severity and evidence timeline.
5. Move the alert through `OPEN → INVESTIGATING → RESOLVED` or `FALSE_POSITIVE`, add an investigator note and verify reviewer timestamps/history.
6. If an approved OpenAI-compatible endpoint is configured, ask why the alert is high risk and request its timeline. Verify every factual statement cites an `[E#]` item and that insufficient evidence produces an explicit limitation. The copilot must remain read-only.

## Evidence to capture for the thesis

- Git commit, configuration profile (without secrets), migration version and test output.
- Dataset origin/manifest/hash, chronological split, feature schema and random seed.
- Candidate metrics and latency generated by the training command, clearly separated by data origin.
- Selected artifact hash/model version and risk-policy version.
- Screenshots of the business ledger, alert contributions, evidence timeline and copilot citations.
- Known limitations: synthetic-data optimism, unavailable ground truth, Redis/object-storage/Compose verification status and provider/data-governance assumptions.
